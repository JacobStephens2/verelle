## Ranked findings

### 1. The plan commits to a non-device posture before establishing that the product is not a Class II contraceptive application

- **Severity:** Critical
- **Location:** [D1 and OQ-4](/home/jacob/verelle/docs/plans/verelle-plan.md:78), [Phase 3 household use](/home/jacob/verelle/docs/plans/verelle-plan.md:164), and [Phase 7 regulatory gate](/home/jacob/verelle/docs/plans/verelle-plan.md:172)
- **Problem:** D1 treats “charting tool for instructed couples” plus disclaimers and competitor behavior as sufficient to avoid the medical-device path. The planned function nevertheless transforms user observations into a user-specific current fertility status and fertile-window bounds, and the plan explicitly anticipates couples using an “infertile” result to avoid pregnancy. The FDA's [current PYT classification](https://www.accessdata.fda.gov/scripts/cdrh/cfdocs/cfPCD/classification.cfm?id=PYT) covers software designed to provide fertility information for preventing pregnancy; it is Class II under 21 CFR 884.5370. The [Natural Cycles decision](https://www.accessdata.fda.gov/cdrh_docs/reviews/DEN170052.pdf) also identifies clinical performance, human factors, hazard analysis, and software validation as special controls. Whether Verelle's precise intended use is regulated is **needs verification**, but existing unchallenged apps and marketing disclaimers do not establish the exemption. OQ-4 waits until Phase 7, after roughly 14–22 effort-weeks through Phase 3 and after real household use of the output.
- **Failure scenario:** Phases 1–6 are built around computed “fertile / infertile” guidance. Late counsel or FDA feedback concludes that the intended use falls under product code PYT and requires a 510(k), clinical evidence, quality-system controls, and different labeling. The solo-project economics no longer work; the engine, validation strategy, launch plan, and product claims require redesign after most of the irreversible learning cost has been paid.
- **Recommendation:** Add a Phase −1 gate before protocol implementation or human reliance: write the exact intended-use statement, indications, claims, output semantics, user workflow, and avoid/achieve-pregnancy use cases; obtain written advice from FDA-device counsel; and seek FDA feedback, using a [513(g) request](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/fda-and-industry-procedures-section-513g-requests-information-under-federal-food-drug-and-cosmetic) if a formal classification view is needed. The gate must produce either (a) a documented non-device/enforcement-discretion basis that covers the actual workflow, (b) a funded regulatory plan with the required controls and evidence, or (c) a stop/re-scope decision that removes computed fertility guidance. Do not start M1 or let users rely on fertility-status output until this gate is closed.
- **Confidence:** High; needs verification

### 2. The cited source does not define the rule system that the conformance corpus is supposed to prove

- **Severity:** Critical
- **Location:** [FR-5 and NFR-7](/home/jacob/verelle/docs/plans/verelle-plan.md:31), [D3](/home/jacob/verelle/docs/plans/verelle-plan.md:82), and [Phase 1](/home/jacob/verelle/docs/plans/verelle-plan.md:160)
- **Problem:** The plan names the Boland Institute [model web page](https://www.marquette.edu/nursing/institute-natural-family-planning/model.php) as the source to transcribe. That page describes biomarkers, target populations, research, and instruction services, but it does not publish an executable regular-cycle or postpartum rule specification. Marquette-hosted evidence also shows distinct [2005](https://epublications.marquette.edu/nursing_fac/5/) and [2013](https://epublications.marquette.edu/nursing_fac/154/) postpartum protocols and [revisions published in 2023](https://epublications.marquette.edu/nursing_fac/981/). The draft does not select a protocol version, define a source hierarchy, identify licensed/current teaching materials, or establish that the instructor reviewer is independently deriving expected results rather than reviewing vectors authored from the same interpretation. A corpus can be 100% self-consistent and still encode the wrong method.
- **Failure scenario:** The developer infers a missed-reading or postpartum transition rule from an article, an old handout, or the monitor's behavior. The spec and golden vectors are authored from that same inference, so CI remains green and a high-level review misses the edge case. A user receives “infertile” on a day the current taught protocol treats as fertile, defeating the core correctness and safety outcome.
- **Recommendation:** Before Phase 1 coding, acquire the complete, current, authoritative materials for every shipping protocol and confirm the right to implement and distribute the resulting rules. Pin each protocol by title, issuer, revision, and effective date; define precedence and a conservative result for missing or ambiguous inputs; create a traceability ledger from every rule to source location to independently derived vectors; and require a credentialed instructor to sign the versioned specification and boundary-case corpus. Add a hazard analysis and a second independent check of every transition capable of producing “infertile.” If the authoritative source package cannot be obtained, stop the computed-status feature.
- **Confidence:** High; needs verification

### 3. The encrypted sync design cannot perform the stated LWW and idempotency semantics

- **Severity:** High
- **Location:** [D11](/home/jacob/verelle/docs/plans/verelle-plan.md:98), [EncryptedRecord and Observation models](/home/jacob/verelle/docs/plans/verelle-plan.md:121), and [concurrency claim](/home/jacob/verelle/docs/plans/verelle-plan.md:152)
- **Problem:** The HLC used to choose a last writer is inside ciphertext, so the server cannot compare it. The clear server sequence orders arrival, not user intent. At the same time, record_id deduplication is said to make retries idempotent, while edits and deletes reuse the logical record keyed by couple/date/marker type; the draft never distinguishes a logical record ID from an immutable write/version ID or says whether the server retains every version. The original [HLC design](https://cse.buffalo.edu/~demirbas/publications/hlc.pdf) preserves causal order and keeps timestamps near physical time; it does not reveal a true “last” event for concurrent offline writes, and the plan supplies no deterministic concurrent tie-breaker. These are contradictory protocol semantics, not missing implementation detail.
- **Failure scenario:** Both partners edit the same marker offline. The newer user edit arrives first and the stale edit arrives second. A server upsert picks stale arrival order; a record-ID dedupe rejects one legitimate revision; or clients receive versions in different orders and choose different winners. A tombstone racing an edit can then resurrect or erase the observation. The user has an acknowledged local write but the reconciled chart silently loses it, violating NFR-1 and M1.
- **Recommendation:** Specify and review a sync state machine before fixing the Phase 1 store schema. Separate logical record IDs from unique immutable operation IDs; define exactly what the server appends, deduplicates, compacts, and exposes through a transactional cursor; choose authenticated version metadata and a deterministic merge rule that every client can evaluate; define tombstone and new-device bootstrap behavior; and state the privacy cost of any clear metadata. Gate implementation on exhaustive/model-based convergence tests covering concurrent edit/edit and edit/delete, retries before and after response loss, clock skew, process death between local commit and enqueue, cursor restart, restore/replay, and three-device histories. Acceptance must prove convergence and no loss of an acknowledged write, not merely exercise an “LWW conflict.”
- **Confidence:** High

### 4. The key lifecycle is gated after storage and real local data have already committed to it

- **Severity:** High
- **Location:** [D5](/home/jacob/verelle/docs/plans/verelle-plan.md:86), [D8](/home/jacob/verelle/docs/plans/verelle-plan.md:92), [Phase 1 store schema](/home/jacob/verelle/docs/plans/verelle-plan.md:160), [Phase 2 real-data gate](/home/jacob/verelle/docs/plans/verelle-plan.md:162), and [Phase 3 key-design gate](/home/jacob/verelle/docs/plans/verelle-plan.md:164)
- **Problem:** The plan postpones the key-exchange/re-key design until Phase 3, but Phase 1 creates the persistent schema and Phase 2 records real, accountless data. The draft has no state transitions for converting local data to an account, linking pre-existing data into a couple, adding another device, changing a password without losing a data key, using a recovery code, accepting a partner re-share, unlinking while another device has queued old-key writes, or rotating and destroying epochs. “Argon2id from passphrase → separate auth hash and data key” also does not establish whether the server sees a reusable authentication secret or how multi-device enrollment remains zero knowledge. The current crypto tests only prove envelope interoperability, not these lifecycle invariants.
- **Failure scenario:** Phase 2 accumulates household data. During Phase 3 enrollment and couple linking, a partial import encrypts some rows under an individual key and some under the couple key. A retry duplicates observations, or a password change strands a wrapped key. Later, one partner unlinks while the remaining partner's offline phone continues creating old-epoch ciphertext; the departed partner still holds that epoch, so “future data is dark” depends on server authorization rather than the claimed re-key invariant.
- **Recommendation:** Move a complete key/data lifecycle ADR ahead of the Phase 1 schema and any real-data acceptance gate. It must define device identity keys, account and dataset keys, password/auth separation, per-device/member wrapping, recovery-code custody, key epochs, password change, device loss/revocation, link merge policy, atomic local-to-synced import, treatment of queued old-epoch operations, unlink completion semantics, and protection against stale or malicious-server replay. Have an independent application cryptographer review the design against a written invariant matrix. Add crash-injection and multi-device adversarial tests; “unlink dark” must be tested with an offline remaining device, an offline departed device, a compromised server, retries, and restored backups.
- **Confidence:** High

### 5. Account deletion is not defined for blind shared records or backup restoration

- **Severity:** High
- **Location:** [FR-11](/home/jacob/verelle/docs/plans/verelle-plan.md:37), [NFR-6](/home/jacob/verelle/docs/plans/verelle-plan.md:48), [couple/record model](/home/jacob/verelle/docs/plans/verelle-plan.md:121), and [deletion verification](/home/jacob/verelle/docs/plans/verelle-plan.md:202)
- **Problem:** FR-11 promises full account and server-data deletion, but the acceptance check only verifies that live server rows are gone. [Chapter 19.373 RCW](https://app.leg.wa.gov/RCW/default.aspx?cite=19.373&full=true) gives consumers deletion rights across the entity's network, including archived/backup systems on a permitted delayed schedule, and requires downstream parties that receive a request to act. The server's blind records are keyed to a couple, while record attribution is encrypted. The plan does not say which data concerns which consumer, whether one partner may delete shared observations, how the other partner's rights are preserved, how tombstones survive a database restore, or when encrypted backups and audit records are purged. Whether every ciphertext/metadata element receives identical legal treatment is **needs verification**, but the law's broad reproductive-health and inferred-data definitions make “the server only has ciphertext” an unsafe compliance shortcut.
- **Failure scenario:** One partner deletes an account after separation. Deleting the whole couple dataset destroys the other partner's chart; deleting only account and membership rows leaves records attributable to the requester in live storage and nightly backups. Months later a restore reintroduces supposedly deleted metadata or ciphertext. The product cannot demonstrate compliance and cannot meet its own “full server-data deletion” promise.
- **Recommendation:** Before the schema is fixed, obtain a counsel-approved data inventory and ownership/subject model for account metadata, couple membership, observations, audit events, billing links, push tokens, and backups. Define account deletion, unlink, per-observation deletion, and whole-couple destruction separately; define processor notifications and retention exceptions; keep a deletion manifest that is reapplied after every restore; and set a backup purge deadline within the legal bound. The deletion E2E gate must inspect all live tables, caches, audit stores, processors, and backup inventories, then restore the oldest retained backup and prove the deletion manifest prevents resurrection.
- **Confidence:** High; needs verification

### 6. The 10-second propagation SLO is undefined across mobile execution states and omits its delivery infrastructure

- **Severity:** Medium
- **Location:** [NFR-3 and NFR-9](/home/jacob/verelle/docs/plans/verelle-plan.md:45), [components](/home/jacob/verelle/docs/plans/verelle-plan.md:104), [Phase 3](/home/jacob/verelle/docs/plans/verelle-plan.md:164), and [observability](/home/jacob/verelle/docs/plans/verelle-plan.md:215)
- **Problem:** The draft assumes opaque “sync now” pushes but names no APNs/FCM component, device-token lifecycle, credentials, failure handling, metrics, or platform acceptance test. It also does not define whether “online device” means the app is foregrounded, backgrounded, suspended, force-quit, or in Android Doze. Apple documents [background notification](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app) as low-priority and not guaranteed, and Android [defers network and normal-priority background sync during Doze](https://developer.android.com/training/monitoring-device-state/doze-standby). A ≤10-second p95 can be meaningful for active clients, but it cannot be asserted uniformly for every network-connected phone state.
- **Failure scenario:** The Phase 3 gate runs with both apps foregrounded and meets 10 seconds. In household use, the receiving app is suspended or in Doze; the opaque ping is throttled or deferred, so the displayed chart is stale for minutes or until launch. Users reasonably interpret “both see the same chart” and the SLO as freshness guarantees the platform cannot provide.
- **Recommendation:** Split the requirement by explicit state. For foreground clients, define a WebSocket or bounded-polling path and measure end-to-end p95 from committed local write to rendered remote state. For background clients, specify best-effort APNs/FCM invalidation, sync-on-resume, a visible last-synced/freshness indicator, and no hard 10-second promise. Add APNs/FCM as dependencies with token rotation/removal, provider-response metrics, retry/collapse behavior, and tests for foreground, background, force-quit, notification-disabled, Doze, network transition, and stale-token cases.
- **Confidence:** High

### 7. The plan invokes incident response but contains no breach-response control or launch gate

- **Severity:** Medium
- **Location:** [C-4](/home/jacob/verelle/docs/plans/verelle-plan.md:70), [Phase 7 “incident response per §6”](/home/jacob/verelle/docs/plans/verelle-plan.md:172), and [§6 operations](/home/jacob/verelle/docs/plans/verelle-plan.md:176)
- **Problem:** The plan correctly treats the [FTC Health Breach Notification Rule](https://www.ftc.gov/system/files/ftc_gov/pdf/hbnr_final_rule_04_25.pdf) as material, but §6 has monitoring and backup operations only—no incident classification, containment, evidence preservation, key-compromise analysis, notification decision, processor contacts, counsel escalation, or tabletop. The FTC rule requires notices after covered breaches, sets deadlines, and places the burden of demonstrating compliance on the vendor. [Washington law](https://app.leg.wa.gov/RCW/default.aspx?cite=19.373&full=true) also requires reasonable security and binding processor instructions. Exact HBNR coverage for each Verelle data flow is **needs verification**, especially because the rule turns on the capability to draw from multiple sources and on whether information is secured, but the plan cannot safely substitute “ciphertext only” for an incident process.
- **Failure scenario:** An auth database, push-token table, backup credential, or client build pipeline is compromised during beta. The solo operator can see an alert but cannot determine which health-linked metadata or keys were exposed, which users and processors are affected, whether encryption safe-harbor conditions remain intact, or what notice clock has started. Evidence decays while the response is improvised, increasing user harm and regulatory exposure.
- **Recommendation:** Add a pre-beta launch gate for a counsel-reviewed incident-response and breach-notification runbook. Name the decision owner and backup contact; classify data/key compromise scenarios; preserve logs without adding sensitive content; inventory processor contractual notice contacts; define containment and credential/key rotation; map user, FTC, media, and state notices to deadlines; prepare message templates; and run one tabletop covering stolen server/backup credentials plus one covering a malicious client release. Record detection-to-triage and triage-to-counsel targets and require corrective actions to close before launch.
- **Confidence:** High; needs verification

## Pre-mortem: likely causes of failure after six months

1. The project spends its limited calendar on the engine and native bindings, then a late regulatory opinion says that the computed fertility output needs a Class II path. The business cannot fund the evidence and controls, so otherwise working code is abandoned or stripped of its core value.
2. A protocol revision or postpartum boundary is absent from the single source used to author both the spec and vectors. Green CI creates false confidence, a real user receives a wrong infertile result, and the first safety incident ends instructor and community trust.
3. Two offline devices edit or delete the same day, and stable-record dedupe plus arrival ordering discards an acknowledged revision. The discrepancy is discovered only after the chart has influenced a decision, breaking the founding “zero lost entries” promise.
4. Local data, couple keys, and membership epochs evolve in different phases without one transition model. A link, recovery, password change, or unlink produces stranded data or old-key ciphertext, and fixing it requires a destructive migration precisely when a relationship is sensitive.
5. A deletion or security incident reaches backups, processors, or mobile credentials that the runbooks do not cover. The solo operator restores or retains data that should stay deleted, misses an evidence/notification step, and turns a bounded technical event into a privacy and legal failure.

## Final assessment

### 1. Verdict

REJECT

### 2. Blocking issues

1. D1's non-device premise is unverified at the exact planned intended use and is gated far too late. A formal, early regulatory disposition may invalidate the product or require a fundamentally different program.
2. The named protocol source does not establish the complete, current regular and postpartum rules. The proposed corpus gate cannot prove clinical/protocol correctness without authoritative versioned sources and independent derivation.
3. The sync, key, and deletion lifecycles are not coherent enough to freeze the Phase 1 schema or put real data through Phase 2 without avoidable loss, access, and compliance risk.

### 3. Highest-value changes

1. Move regulatory classification and authoritative protocol-source acquisition into a no-code viability phase; stop if either gate fails.
2. Before defining persistence, write and independently review the sync state machine, key/membership lifecycle, and data deletion/restore model as one set of cross-referenced invariants.
3. Replace broad promises with state-specific, adversarial acceptance gates for protocol safety, acknowledged-write durability, unlink/recovery, deletion after restore, mobile freshness, and incident response.

### 4. Revised plan outline

1. **Viability disposition before scaffolding:** resolve OQ-1; pin intended use and obtain regulatory disposition; acquire and license/authorize the exact regular and postpartum protocol sources; record explicit stop/re-scope criteria.
2. **Safety and lifecycle specifications:** produce the versioned protocol spec and hazard analysis; a requirement-to-source-to-vector ledger; the sync state machine; key/device/member epoch model; data inventory, ownership, retention, and deletion model; and state-specific freshness SLOs. Independent reviewers sign the relevant artifacts before schemas are fixed.
3. **Local engine proof without reliance:** implement the smallest core and CLI from independently derived vectors; include ambiguity-to-fertile/no-result behavior, property tests, and instructor sign-off. Do not use computed results for pregnancy decisions until the regulatory gate permits it.
4. **Crash-safe single-device vertical slice:** define atomic observation-plus-outbox commits, migration/rollback rules, storage-exhaustion behavior, and export/recovery. Pass crash injection, schema upgrade/downgrade, and local import tests before accepting household data.
5. **Two/three-device E2EE sync spike:** implement only enough server and clients to model enroll, link, concurrent writes, recovery, password change, unlink, deletion, backup, restore, and replay. Pass convergence and key-lifecycle adversarial gates before choosing production infrastructure or starting M1.
6. **Staged household pilot:** order platforms from the actual founding devices; begin with noncritical shadow comparison against instructor-validated charts; require a rollback/export path, freshness indicators, restore drill, and an explicit period with zero unexplained divergence before relying on output.
7. **Public-readiness tranche:** add privacy/processor contracts, deletion-after-restore evidence, incident-response table-tops, store-policy ADRs, payment lifecycle, beta safety/usability evidence, and launch/abort criteria. Only then add web breadth and defer watches until value metrics justify the surface.
